01一句話重點

說「檢查一下」不算驗證；說「做好一點」不算規格。
先寫好「完成的定義」，再決定要不要加上 Loop 或 Graph。

上一週學的是「當老闆」：交辦工作時講清楚要什麼成品、有什麼限制、怎麼算做完，重點是不要讓 AI 猜。這週往前一步——老闆不能一直盯著 AI 改，要把「盯」這件事本身設計成流程，交給系統去跑。

03核心觀念

為什麼要換成 Code Agent

網頁版聊天介面讀不到自己電腦裡的檔案；Code Agent（例如 Antigravity、Claude Code、Codex、OpenCode）則是直接開一個專案資料夾，讓 AI 有權限讀寫裡面的檔案。課堂以 Antigravity 示範，但做法四套工具都通用。

Work AgentCode Agent
代表ChatGPT Work、Claude、OpenWorkerAntigravity、Claude Code、Codex
預設看到成品和摘要每一行修改（diff）
版本控制要自己記得git 是基本盤
驗證多半靠人讀跑測試、跑腳本
資料夾／Skills✓✓

兩個工程習慣：git 與可執行的檢查

git每一步都能回到上一版，也看得出 AI 到底改了什麼。
可以執行的檢查「做完了」不是 AI 說了算，是腳本說了算。

對 AI 說「檢查一下」，不算驗證。驗證要是一個能重複執行、會回報通過或失敗的東西。

員工手冊：AGENTS.md

各家 Code Agent 都會在開工前讀專案根目錄的規則檔：通用的是 AGENTS.md，Claude Code 讀 CLAUDE.md，Gemini 讀 GEMINI.md。三個小提醒：

  • 別寫太長：Antigravity 的規則檔上限約 12,000 字元，細節拆到 skill 檔。
  • 只維護一份：GEMINI.md 的優先序高於 AGENTS.md，兩份並存容易互相打架。
  • Claude Code 共用寫法：在 CLAUDE.md 裡只寫一行 @AGENTS.md，引用同一份規則。

寫 Prompt vs 寫 Loop

老闆一直盯：AI 做出一版 → 你發現第 5 頁字太多 → 再交辦一次 → ……這個「你檢查、你再下指令」的來回，本身就是一個 loop，只是現在由人當黏著劑。Loop Engineering 的想法是：不要再寫這一輪的 prompt，改寫一份會自己反覆執行的規格。

寫 Prompt寫 Loop
寫的內容這一輪要做什麼目標、完成標準、驗證方式、停止規則
下一步誰決定你讀完結果再寫下一句系統依檢查結果決定
寫幾次每一輪都寫寫一次，跑很多輪
你的角色黏著劑設計者、審查者

最早的 loop 只有一行：Geoffrey Huntley 的 Ralph loop（2025 年 7 月），把同一份 PROMPT.md 每一輪重餵一次。

while :; do cat PROMPT.md | claude ; done

看起來很笨，但真的會動——讓它運作的是 prompt 以外的東西：重複、檢查、用檔案記進度。

一個 Loop 要寫清楚五件事

🎯 目標要什麼成品
🚧 限制哪些不能動
✅ 完成標準怎麼算做完
🛑 停止條件做不到時何時停
⏰ 觸發什麼時候開始跑

前三件就是上週「當老闆」學過的。完成標準又分兩種檢查：

  • 程式檢查：測試有沒有過？連結斷了沒？每頁有沒有出處？——能寫成腳本的就寫成腳本。
  • AI 審查：內容有沒有忠於來源？說法有沒有講反？——要開新的對話，只給成品和來源，不要叫 AI 審自己的作品。

Loop 也要剎車：設硬上限（例如最多改 3 輪）、資料不足就停、不要用不相干的知識硬湊。而且一個 loop 花的 token 遠多於聊天。沒人看管的 loop，就是在沒人看管下犯錯的 loop。

Graph：改變的是「誰在控制」

在 loop 裡，AI 決定下一步（反覆改作業，改到檢查表全過）；在 graph 裡，流程是你事先畫好的——像學校的申請流程：系辦 → 院 → 教務處，不能跳關，卡住會退回特定一關。

其實三者都是圖：Prompt 是一個節點跑一次；Loop 是加一條「回到自己」的邊；Graph 的退回邊可以接到任何一個節點。一個順利跑完的 graph，看起來就是一條流水線。

好的 graph：小圈轉得很快、大圈很少轉。錯誤要在離源頭最近的地方被抓到；如果常常從最後一關退回起點，代表檢查應該往前移。

讓問題告訴你需要多少結構

  1. 先用 Prompt
    一次性、人會看
  2. 升級成 Loop
    一直重複說同樣的修正
  3. 拆成 Graph
    每次都整份重來、各階段標準不同

不一定要堅持做到 graph。三種做法的對照：

PromptLoopGraph
流程誰決定你，即時決定AI，在規格內你，事先畫好
出錯怎麼修你發現、你下指令整份再跑一輪退回出錯的那一關
人在哪裡介入隨時最後驗收指定關卡
適合一次性、人會看標準明確的重複任務多階段、多人使用

04實作紀錄

實作一：先討論，再建 LLM Wiki

上週是「一句話叫 AI 依 Karpathy 的 LLM Wiki 建 AGENTS.md 和資料夾」；這週改成先讓 AI 訪談我、整理需求，確認後才建檔。

  1. 準備建一個專案資料夾 → git init → 把 3–5 篇 LLM 論文放進 raw/（raw/ 不要放個資或機密文件）→ 用 Antigravity 開啟資料夾。
  2. 開場 prompt附上 LLM Wiki 構想，明確要求「先不要建任何檔案，一次問一個問題」。
  3. 被訪談AI 應該問到：讀者是誰、要哪些頁面類型、用什麼語言、出處要多細、論文互相矛盾怎麼辦、一次一篇還是批次、之後要產出什麼、lint 要檢查什麼。
  4. 確認需求摘要 → 生成 AGENTS.md逐條對照：摘要裡說的，手冊裡都有寫進去嗎？
  5. Ingest 1–2 篇，然後 commit產生 wiki/index.md、wiki/log.md，再 git commit -m "first ingest"。
這是 Karpathy 的 LLM Wiki 構想（附上 gist）。
我想用它來整理＿＿＿＿的論文。
先不要建立任何檔案。請一次問我一個問題，幫我釐清需求，大約 8–10 題。
問完後整理成需求摘要給我確認，確認後才生成 AGENTS.md 和資料夾。

實作二：主題 → HTML 簡報

同一個 wiki、同一個模型、同一件事（例：用 wiki 內容做一份「多模態 RAG」HTML 簡報），只換做法：

  1. Prompt 版一句話叫它做，然後開始一直修：第 5 頁字太多、某個數字找不到出處、相關論文只用了一部分、某篇論文的結論講反了……我自己就是那個 loop。
  2. Loop 版把修正寫成一份 SKILL.md 規格：只用 wiki；程式檢查（每頁有出處、引用存在、數字找得到、8–15 頁、渲染後沒有溢出）；AI 審查（新對話，只給簡報和引用來源）；每一輪只修檢查報告列出的問題；全過、改滿 3 輪、或相關論文少於 3 篇（開始前）就停。跑起來大約 3 輪就能交件，我只要看最後的報告。
  3. Graph 版先畫好流程：檢索 wiki → 覆蓋率關卡 → 證據卡 → 大綱 → 人確認 → 逐頁稿 → 忠實度檢查 → 渲染 HTML → 渲染檢查 → 交件。每一關規定只能看什麼、不能做什麼（例如渲染關不能改任何一個字），錯在哪一關就退回哪一關。

Graph 的每一格裡面還是 loop：graph 決定流程，loop 負責每一格的反覆修正。所有狀態都存成檔案（sources.md、cards/、outline.md、drafts/、deck.html、report.md），每一關的產出都能打開看、放進 git、單獨重跑。流程本身也可以寫成 workflow 檔放進 .agents/workflows/，用斜線指令呼叫。

拆解你自己的工作

先用紙畫，不要急著叫 AI 做：

  • 可以拆成哪幾個節點？每個節點的輸入、輸出是什麼檔案？
  • 每個節點怎麼檢查——程式、人，還是 AI 審查？
  • 人要在哪一關介入？出錯時退回哪裡？
  • 其實 prompt、loop 還是 graph 就夠了？

06我的反思

  • 這個筆記站就是我練習這週觀念的地方：AGENTS.md 是員工手冊，scripts/check.py 是「完成的定義」，.agents/workflows/add-lesson.md 則是新增一週筆記的 loop 規格。
  • 以前我請 AI 改網頁，常常是「看一眼 → 覺得怪 → 再講一次」；現在我會先問自己：這個修正我是不是已經說第二次了？如果是，就該把它寫進規則或檢查腳本。
  • 我覺得最有用的一句是「錯誤要在離源頭最近的地方被抓到」。寫筆記也一樣，大綱先確認，比整頁寫完再退回來便宜很多。
